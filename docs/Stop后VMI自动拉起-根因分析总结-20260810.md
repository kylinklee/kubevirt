## 1. 问题描述

- **场景**：生产集群从 KubeVirt v1.2.0 直接升级 v1.6.6（K8s 1.31，runStrategy 一直为 `RerunOnFailure`）。
  对运行中的 VM 执行 **Stop**（优雅关机），v1.6.6 下 VMI 在关机成功后 **约 65 秒被置为 Failed 并自动拉起**（RerunOnFailure 重启）。
- **v1.2.0 对照**：同样操作，VMI 从 Running 直接跳到 **Succeeded**（不重启）。优雅关机本身**两版本都成功**
  （ACPI_POWER_BTN → guest systemd 响应 → 7s 内 `Shutoff reason Shutdown`）。
- **关键现象**：shutoff 后 virt-handler 出现 **65 秒日志空白**（无任何 reconcile 日志），随后 Failed。

## 2. 最终根因链（2026-08-10 探针日志证实）

```
① 用户执行 Stop → virtctl → virt-api → virt-controller 删 VMI（DeletionTimestamp）
② virt-handler 优雅关机成功：Signaled graceful shutdown → domain shutoff（~7s）
③ virt-handler updateVMIStatus：Update VMI status 成功（06:10:28.750）
   → SetExpectations(key, 1, 0)：期望 informer 收到 1 个 VMI 更新事件来"清账"
④ ★ 根因：VMI 更新事件（API server watch → vmiInformer → updateFunc）46 秒+ 未到达
   → expectations 一直未满足（add=1）
⑤ 期间所有 reconcile（AddAfter 5s、domain shutoff 事件）在 execute() 入口
   被 SatisfiedExpectations(key)==false 拦截 → return nil 静默跳过（不打日志）
   → 表现：65 秒完全空白，virt-handler 未及时判 Succeeded、未发 DeleteDomain
⑥ virt-launcher waitForFinalNotify 45s 超时 → 退出 → pod 消失
⑦ virt-controller（vmi 控制器 lifecycle.go:416）：VMI Running + pod 不存在
   → 无条件写 VMI=Failed（无 DeletionTimestamp 豁免）
⑧ VMI 删除事件终于到达 informer → addDeleteFunc → SetExpectations(0,0) 清账
   → virt-handler 恢复 reconcile——但 domain 已消失 → Failed 成立
⑨ RerunOnFailure：VMI=Failed → 自动拉起（新 VMI）
```

**一句话**：**v1.6.6 下 virt-handler 的 VMI informer 更新事件延迟 ~46s（未消费 expectations），导致所有 reconcile 被静默跳过 65s，virt-launcher 超时退出 → pod 消失 → virt-controller 写 Failed → 自动拉起。**

## 3. 决定性证据：探针日志时间线（2026-08-10 06:09-06:12，commit 0ea9bfdd49）

```
06:10:28.750  updateVMIStatus: VMI Update API call succeeded   ← Update 成功，SetExpectations(1,0)
06:10:28.751  execute: expectations not satisfied, skipping reconcile  ★ 第一次出现（domain 事件触发）
              → 之后所有 reconcile 静默跳过 = 65 秒空白
06:11:14      ⏱+46s  execute: expectations not satisfied, skipping（virt-launcher 45s 超时退出 → domain 消失）
06:11:21      ⏱+6.4s execute: expectations not satisfied, skipping
06:11:36      ⏱+15.2s vmiExists=false（VMI 删除事件到达 → addDeleteFunc 清账 → 恢复）
06:11:47      新 VMI 自动拉起 → 正常 reconcile 循环（expectations 竞态毫秒级恢复）
```

**补充观察**：
- updateVMIStatusFromDomain 全部子函数毫秒级完成（[debug] 探针证实）——**不是卡点**
- ExpectationsTimeout = 5 分钟（pkg/controller/expectations.go:48）——65s 恢复**不是超时**，是删除事件清账
- domain informer 事件正常（06:10:28.751 的 domain 事件触发了 execute）——**只有 VMI informer 的更新事件延迟**

## 4. 已排除的假设（勿重复排查）

| # | 假设 | 排除依据 |
|---|------|---------|
| 1 | 优雅关机失败（ACPI/guest 问题） | 两版本日志：ACPI_POWER_BTN → guest systemd → 7s 内 shutoff:shutdown ✓ |
| 2 | QEMU/libvirt 版本差异 | 两版本环境完全一致（libvirt 9.10.0 / QEMU 8.2 virt-8.2） |
| 3 | 方案A（handleVMIShutdown 快速路径，50a61a3d21） | 生产验证无效——requeue 也被 expectations 拦截 |
| 4 | updateVMIStatusFromDomain 内部卡点（文件系统/RPC） | [debug] 探针：所有子函数毫秒级（含 updateIsoSizeStatus/netStat） |
| 5 | updateVMIStatus 后半段卡点（conditions/checksum/Update API） | [debug] 探针：毫秒级完成 |
| 6 | 409 乐观锁冲突是根因 | 附带现象——重试写入的也是 Failed；v1.2.0 也偶发 409（新 VMI 启动） |
| 7 | migration 控制器 handler 卡住阻塞 informer | handlers 都是 queue.Add 快速操作（migration-source.go:593-620） |
| 8 | expectations 超时（5 分钟）导致 65s 后恢复 | 65s 恢复靠 VMI 删除事件清账，非超时 |
| 9 | SELinux 修复（e0a6c6e275/fd6c08836e）引入问题 | isSELinuxEnabled 只影响网络配置路径；updateSELinuxContext 用户环境快速失败 |
| 10 | virt-controller 与 virt-handler 状态竞争是根因 | 竞争（409）是后果；virt-controller 写 Failed 是"pod 消失"的正确反应 |
| 11 | 客户端（virtctl v1.2.0）导致 watch 延迟 | 理论排除（watch 是 virt-handler↔API server 闭环）；**待实验确认**（用 v1.6.6 virtctl 重测） |

## 5. 当前待办（按优先级）

1. **【根因谜题】为什么 VMI 更新事件 46s 未到达 updateFunc**——候选：
   a. v1.6.6 的 vmiInformer/reflector 配置差异（vs v1.2.0——virtinformers 工厂）
   b. API server watch 流问题（但 v1.2.0 同集群正常，排除环境网络？）
   c. virt-handler 的 reflector goroutine 卡住（dump 栈可确认——Stop 后 30s 内 SIGQUIT）
2. **【实验验证】客户端版本排除**：用 v1.6.6 virtctl（或 kubectl 直接调 /stop subresource）重测一次 Stop
   ——问题依旧 → 客户端排除；消失 → 深挖 virtctl 差异
3. **【修复方向】方向B（兜底，独立于根因）**：virt-launcher `waitForFinalNotify` 在 domain 已
   `shutoff:shutdown` 时不超时退出 → pod 不消失 → virt-controller 不写 Failed → 即使
   virt-handler 卡 65s 最终也判 Succeeded，不重启
4. **【收尾】PR #18721（ACPI 修复，Draft+/hold）去留**：根因闭环后决定
5. **【收尾】移除调试日志探针**（见第 6 节清单）——定位完成、修复验证通过后移除

## 8. 两版本行为差异汇总（与本次根因相关）

| 环节 | v1.2.0 | v1.6.6 | 影响 |
|------|--------|--------|------|
| updateFunc 清账 | `LowerExpectations(1,0)`（递减） | `SetExpectations(0,0)`（清零） | 等价（均需事件到达） |
| expectations 机制 | 相同（pkg/controller） | 相同 | 无 |
| informer 注册 | vmiSourceInformer（addFunc/deleteFunc/updateFunc） | vmiInformer（addDeleteFunc/addDeleteFunc/updateFunc） | Add/Delete 合并，均清账 |
| migration 控制器 | 无（迁移逻辑在主控制器） | 独立 ×5 worker + informer handlers | handlers 快速，无阻塞 |
| VMI 更新事件到达 | 正常（毫秒级） | ★ 46s+ 延迟（根因） | **待查** |
