# Stop 后 VMI 自动拉起问题：根因分析总结与当前进展（2026-08-10 最终版）

> 本文档是 kubevirt 升级（v1.2.0 → v1.6.6）"Stop 后 VMI 自动拉起"问题的**最终根因分析快照**。

## 1. 问题描述

- **场景**：生产集群从 KubeVirt v1.2.0 直接升级 v1.6.6（K8s 1.31，runStrategy 一直为 `RerunOnFailure`）。
  对运行中的 VM 执行 **Stop**（优雅关机），v1.6.6 下 VMI 在关机成功后 **约 65 秒被置为 Failed 并自动拉起**（RerunOnFailure 重启）。
- **v1.2.0 对照**：同样操作，VMI 从 Running 直接跳到 **Succeeded**（不重启）。优雅关机本身**两版本都成功**
  （ACPI_POWER_BTN → guest systemd 响应 → 7s 内 `Shutoff reason Shutdown`）。
- **关键现象**：shutoff 后 virt-handler 出现 **65 秒日志空白**（无任何 reconcile 日志），随后 Failed。

## 2. 最终根因链（2026-08-10 三层日志证实）

```
① Stop → virt-controller 删 VMI（DeletionTimestamp）+ virt-handler 优雅关机（ACPI 成功，~7s shutoff）
② ★ 触发 VMI 写风暴：virt-handler（updateVMIStatus，每 5s reconcile 必写）+ virt-controller
   （vm/vmi 控制器）高频并发更新同一 VMI → 409 竞争循环 → 写入量倍增
③ ★ 根因：定制后端存储（ccdb）在写风暴下 watch 推送停摆（增量源断，静默无日志）
   → apiserver 的 watch cache 无增量可推 → 所有 VMI watcher 收不到事件
   → virt-handler（source informer）+ virt-controller 全部静默（65s，apiserver 日志零 VMI 请求）
④ virt-handler 的 expectations 卡死：updateVMIStatus Update 成功 → SetExpectations(key,1,0)
   → VMI 更新事件 46s+ 未到达 informer → updateFunc 未清账
   → 期间所有 reconcile（AddAfter 5s、domain shutoff 事件）在 execute() 入口被
     SatisfiedExpectations(key)==false 拦截 → return nil 静默跳过 → 65 秒空白
⑤ 各 watcher 退避重连：virt-handler 的 informer 43s 后重连（starting watch rv=101217）
   → 重连后存储的 revision 读取已损坏："Failed to list key's revision"（Aborted）
   → virt-controller PATCH 422/404、virt-handler PUT 500、row_count not zero 冲突
⑥ virt-launcher waitForFinalNotify 45s 超时 → 退出 → pod 消失
⑦ virt-controller（vmi 控制器 lifecycle.go:416）：VMI Running + pod 不存在 → 写 Failed（无豁免）
⑧ virt-handler 恢复后入口见 VMI 已 Failed → RerunOnFailure 自动拉起
```

**一句话**：**Stop 流程的 VMI 写风暴导致定制后端存储（ccdb）的 watch 推送停摆 + revision 读取失败——apiserver 的 watch cache 因此 65 秒无增量——virt-handler/virt-controller 全部收不到 VMI 事件——virt-handler 的 expectations 未清账导致 reconcile 被静默跳过 65s——virt-launcher 超时退出 → pod 消失 → virt-controller 写 Failed → 自动拉起。** v1.2.0 写风暴弱（无独立 vm 控制器高频竞争），不触发该存储缺陷。

## 3. 决定性证据：三层日志时间线（2026-08-10 10:40 UTC / 18:40 本地）

```
virt-handler（UTC）：
10:40:04.332/490  informer: vmi update event（断连前最后事件，正常到达）
10:40:04.439       execute: expectations not satisfied, skipping reconcile（卡住开始）
10:40:06-12        domain 事件 → execute → not satisfied（★ VMI 事件已断，只有本地 domain 事件）
10:40:47.488       listwatch: starting watch（★ 43s 后重连，rv=101217——退避重连特征）

apiserver（本地）：
18:40:04.278       Stop 请求（202）
18:40:04.466       kubelet POST events（最后一条）
★ 18:40:04.466 → 18:41:09：65 秒内零 VMI 请求（virt-controller 也收不到事件，全局静默）
18:41:10.095/.177  virt-controller PATCH VMI → 422 / 404（★ 重连后恢复，但存储已异常）
18:41:28.302       "Unhandled Error"：rpc error: Aborted = Failed to list key's revision
18:41:28.306       virt-handler PUT VMI → 500（同错误）

后端存储（ccdb，本地）：
18:41:28.301       ★ row_count not zero（key-101554）→ execCcdbSetSync failed → insert failed Err: -1
18:41:04-06        compact key 风暴（events/PVCs/pods...）——发生在停摆后 60s，是结果非原因
```

**关键判读**：
- **apiserver 断连窗口零错误、零 VMI 请求**——apiserver 健康但"没数据可推"（watch cache 增量源断）→ **问题在 apiserver 与存储之间**
- **virt-controller 也静默 65s**（18:40:04.466 → 18:41:09 无 PATCH）——**全局 watch 停摆**，非 virt-handler 独有
- **重连后存储 revision 读取失败**（Aborted/row_count）——**存储侧数据已损坏/不可读**
- **compact（18:41:04）与 409 均在卡顿之后**——是结果/伴随现象，非原因

## 4. 已排除的假设（勿重复排查）

| # | 假设 | 排除依据 |
|---|------|---------|
| 1 | 优雅关机失败（ACPI/guest 问题） | 两版本日志：ACPI_POWER_BTN → guest systemd → 7s 内 shutoff:shutdown ✓ |
| 2 | QEMU/libvirt 版本差异 | 两版本环境完全一致（libvirt 9.10.0 / QEMU 8.2 virt-8.2） |
| 3 | 方案A（handleVMIShutdown 快速路径，50a61a3d21） | 生产验证无效——requeue 也被 expectations 拦截 |
| 4 | updateVMIStatusFromDomain 内部卡点（文件系统/RPC） | [debug] 探针：所有子函数毫秒级（含 updateIsoSizeStatus/netStat） |
| 5 | updateVMIStatus 后半段卡点 | [debug] 探针：毫秒级完成 |
| 6 | 409 乐观锁冲突是根因 | 症状非原因（v1.2.0 也偶发 409）；重试写入的也是 Failed；已证实真正原因是事件未到 |
| 7 | migration 控制器 handler 卡住阻塞 informer | handlers 都是 queue.Add 快速操作（migration-source.go:593-620） |
| 8 | expectations 超时（5 分钟）导致恢复 | 65s 恢复靠事件清账，非超时 |

| 10 | virt-controller 与 virt-handler 状态竞争是根因 | 竞争是后果；virt-controller 写 Failed 是"pod 消失"的正确反应 |
| 11 | 客户端（virtctl v1.2.0）导致 watch 延迟 | 理论排除（watch 是 virt-handler↔apiserver 闭环）；未实验确认 |
| 12 | 存储 compact（18:41:04）导致 watch 中断 | 发生在停摆后 60s（18:41:04 vs 中断 18:40:04.5）——太晚，是结果 |
| 13 | apiserver 主动断开/出错导致 watch 中断 | 断连窗口 apiserver 零错误、其他请求正常（lease/discovery/kubectl）——apiserver 健康 |
| 14 | debugListWatch 包装（71643b6f8b/09b801a4df） | 违反 watch.Interface 契约（ResultChan 同 channel）导致 VM 创建失败，已回退（8ec93b579e） |

## 5. 修复方向（按优先级）

1. **【减轻写风暴】KubeVirt 侧降低 Stop 流程写入量**（治标：降低存储缺陷触发概率）：
   - **A**：virt-handler `updateVMIStatus` 的 Update 409 后**不返回 err**（吞掉，等 AddAfter 5s 自然节奏）——消除 409 重试风暴的源头（改动 ~5 行）
   - **B**：virt-controller `stopVMI`/vm 控制器的 stopRequest 处理**去重**（VM 已在停止中不重复更新状态）——减少 PUT VM/status 竞争
2. **【兜底】方向B**：virt-launcher `waitForFinalNotify` 在 domain 已 `shutoff:shutdown` 时**不超时退出** → pod 不消失 → virt-controller 不写 Failed → 即使存储停摆也不重启
3. **【治本】存储侧**：定制后端存储（ccdb）的 watch 推送停摆 + `Failed to list key's revision` + `row_count not zero` 并发写冲突——**需厂商排查修复**（内部渠道反馈）
4. **【收尾】PR #18721（ACPI 修复，Draft+/hold）去留**：根因闭环后决定
5. **【收尾】移除调试日志探针**（见第 6 节）——修复验证通过后移除

## 8. 两版本行为差异汇总（与本次根因相关）

| 环节 | v1.2.0 | v1.6.6 | 影响 |
|------|--------|--------|------|
| updateFunc 清账 | `LowerExpectations(1,0)`（递减） | `SetExpectations(0,0)`（清零） | 等价（均需事件到达） |
| expectations 机制 | 相同（pkg/controller） | 相同 | 无 |
| informer 注册 | vmiSourceInformer（addFunc/deleteFunc/updateFunc） | vmiInformer（addDeleteFunc/addDeleteFunc/updateFunc） | Add/Delete 合并，均清账 |
| migration 控制器 | 无（迁移逻辑在主控制器） | 独立 ×5 worker + informer handlers | handlers 快速，无阻塞 |
| **Stop 写风暴强度** | **弱**（vm 控制器更新少） | **强**（virt-handler 每 5s 必写 + vm/vmi 控制器高频竞争 409） | ★ 触发存储 watch 停摆 |
| VMI 更新事件到达 | 正常（毫秒级） | ★ 46s+ 延迟（存储 watch 停摆） | **根因** |
