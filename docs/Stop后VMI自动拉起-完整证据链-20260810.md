# Stop 后 VMI 自动拉起问题：完整证据链总结（组件视角，2026-08-10 最终版）

> 本文档以**组件视角**整理整个问题的证据链：每个组件出问题的地方附实际日志，
> 并说明**正常预期**（v1.2.0 对照行为）。新会话续接时先读本文档。
> 配套文档：`docs/Stop流程写风暴-两版本对比.md`（写风暴放大机制）。

---

## 0. 问题与因果链总览

**场景**：KubeVirt v1.2.0 → v1.6.6 升级（K8s 1.31，runStrategy=RerunOnFailure）。对 VM 执行 Stop，
v1.6.6 下 VMI 在优雅关机成功后约 65s 被置 Failed 并自动拉起；v1.2.0 同样操作直接 Succeeded 不重启。

**因果链**（箭头 = 触发，★ = 异常点）：
```
Stop → 首批并发写（virt-controller 删 VMI + virt-handler Update）
→ ★ 存储 watch 推送停摆（静默）→ ★ apiserver watch cache 65s 无增量
→ ★ virt-handler/virt-controller 收不到 VMI 事件（65s）
→ ★ virt-handler expectations 未清账 → reconcile 静默跳过（65s 空白）
→ ★ virt-handler 重连（43s 退避）→ 存储 revision 读取失败（写入 422/404/500）
→ ★ virt-launcher 45s 超时退出 → pod 消失
→ virt-controller 写 Failed → RerunOnFailure 自动拉起
```

## 1. virt-handler

### 异常点 A：expectations 未清账 → reconcile 静默跳过（65s 空白）

**日志证据**（10:40 测试，UTC）：
```json
{"msg":"[debug] execute: expectations not satisfied, skipping reconcile","pos":"vm.go:333","timestamp":"2026-08-10T10:40:04.439727Z"}
{"msg":"[debug] execute: expectations not satisfied, skipping reconcile","timestamp":"2026-08-10T10:40:06.367517Z"}
{"msg":"[debug] execute: expectations not satisfied, skipping reconcile","timestamp":"2026-08-10T10:40:09.396596Z"}
{"msg":"[debug] execute: expectations not satisfied, skipping reconcile","timestamp":"2026-08-10T10:40:12.980547Z"}
```
（06:10 测试同样：46s 内反复出现，期间无任何其他 reconcile 输出）

**机制**：`updateVMIStatus` Update 成功 → `SetExpectations(key,1,0)`（vm.go:1112）→ 等 informer
事件清账（updateFunc `SetExpectations(0,0)`，vm.go:2417）→ 事件不到 → execute() 入口
`SatisfiedExpectations`（vm.go:327）拦截所有 reconcile。

**正常预期**：Update 成功 → 事件毫秒级到达 informer → updateFunc 清账 → 下一次 reconcile 正常执行
（v1.2.0：优雅关机后 66ms 判 Succeeded，无空白）。

### 异常点 B：VMI 更新事件中断 43s（watch 停摆）

**日志证据**（10:40 测试，UTC）：
```
10:40:04.332  [debug] informer: vmi update event   ← 断前最后事件（到达）
10:40:04.490  [debug] informer: vmi update event   ← 断前最后事件（到达）
10:40:04.490 → 10:40:47  无任何 vmi update event（同期只有 domain 事件：
              10:40:06.367 / 10:40:12.980 —— 本地链路正常）
```

**正常预期**：virt-handler 自己 Update 后、virt-controller 的每次 VMI 变更 → MODIFIED 事件
毫秒级到达 handler（v1.2.0 实测正常）。

### 异常点 C：watch 重连（43s 退避，非周期刷新）

**日志证据**（10:40 测试，UTC）：
```
10:40:47.488  [debug] listwatch: starting watch for virtualmachineinstances (labelSelector=...rv=101217)
```
（重连前有 43s 退避间隙 = list() 连续失败，backoffManager 800ms→30s 指数累积）

**正常预期**：5-10 分钟一次的周期刷新（client-go TimeoutSeconds=300~600s 随机，reflector.go:441）
——无退避、无 list 失败、重连后事件流正常。

### 异常点 D：Update 失败（409 风暴 + 500）

**日志证据**：
```json
{"msg":"Updating the VirtualMachineInstance status failed.","reason":"...the object has been modified...","timestamp":"2026-08-10T08:10:05.231Z"}
{"msg":"Updating the VirtualMachineInstance status failed.","timestamp":"2026-08-10T08:10:05.345Z"}
```
（08:10 测试 0.5s 内 14 次 reconcile、多次 409；18:41:28.306 apiserver 侧 PUT VMI → 500）

**正常预期**：status 有变化时 Update 成功；409 偶发（竞争）但重试成功；**500 不应出现**
（500 = 存储 revision 读取失败，见第 4 节）。

## 2. virt-controller

### 异常点 A：Stop 处理后 65s 无任何 VMI 操作（informer 同样收不到）

**日志证据**（apiserver 侧，本地时间）：
```
18:40:04.278  PUT /stop → 202（Stop 请求，virt-api）
18:40:04.466  kubelet POST events（最后一条 VMI 相关）
★ 18:40:04.466 → 18:41:09：65 秒零 VMI 请求
   （期间只有 apiserver lease 409、discovery、kubectl GET——与 VMI 无关）
```

**正常预期**：Stop 后 virt-controller 立即处理 stopRequest（"processing stop request"）→
PATCH VMI DeletionTimestamp → VMI 删除流程推进——**大量 VMI 写操作应在 httplog 可见**。

### 异常点 B：恢复后的写入失败（存储已损坏）

**日志证据**（apiserver，本地）：
```
I0810 18:41:10.095  PATCH VMI → 422
I0810 18:41:10.177  PATCH VMI → 404
I0810 18:41:10.270  PUT VM/status → 409
I0810 18:41:28.269  PATCH VMI → 422
```

**正常预期**：PATCH/PUT 返回 2xx；404（对象读不到）与 422（校验失败）异常——指向存储读取异常。

### 异常点 C：写 Failed（lifecycle.go:416，VMI Running + pod 不存在）

**日志证据**：
```
（07:30 测试）07:31:51  informer: vmi update event（virt-controller 设 Failed 的更新）
（08:10 测试）08:11:10  "processing stop request for VMI with phase Failed" → 自动拉起
```

**正常预期**：pod 存活期间 VMI 保持 Running/优雅关机状态；正常流程中 virt-handler 应抢先
判 Succeeded（v1.2.0）——virt-controller 的 Failed 判定是"pod 消失"的正确反应，但正常流程
pod 不应消失。

## 3. apiserver

### 异常点 A：watch cache 65s 无增量可推（断连窗口零错误、零 VMI 请求）

**日志证据**（本地）：
```
18:40:04.466 → 18:41:09：65 秒内 httplog 无任何 VMI 请求、无任何 watch 错误
（apiserver 其他功能正常：lease 更新 409 是正常竞争、discovery/kubectl 正常响应）
```

**正常预期**：virt-handler/virt-controller 的 VMI 写操作持续出现在 httplog（Stop 流程活跃期）；
watch 流持续推送 MODIFIED。

**说明**：apiserver 健康但"没数据可推"——watch cache 的增量源（存储 watch）断了。
**watch 流内的错误（Aborted）以 watch.Error 事件发给客户端，httplog 不记录**
——所以 apiserver 日志"干净"是假象，客户端实际收到了错误。

### 异常点 B：重连后的存储读取失败（Unhandled Error + 500）

**日志证据**（本地）：
```
E0810 18:41:28.302  status.go:71 "Unhandled Error" err="apiserver received an error that is not an metav1.Status: ... rpc error: code = Aborted desc = /registry/kubevirt.io/virtualmachineinstances/kubevirt/bd7b60cbf8... Failed to list key's revision"
I0810 18:41:28.306  PUT /virtualmachineinstances/... → 500（同一错误）
```

**正常预期**：apiserver 从存储按 revision 读取/写入正常（无 Aborted、无 500）。

## 4. 后端存储（ccdb）

### 异常点 A：并发写事务冲突（同一 revision 重复插入）

**日志证据**（本地）：
```
Aug 10 18:41:28 ccdb.cpp:980]   E key:/registry/kubevirt.io/virtualmachineinstances/...-101554 row_count not zero
Aug 10 18:41:28 ccdb.cpp:405]   E key:...execCcdbSetSync failed, ret: 0, count: 1, key:101558
Aug 10 18:41:28 ccdb_shim.cpp:478] E failed to insert /registry/kubevirt.io/virtualmachineinstances/... Err: -1
```

**正常预期**：并发事务分配**唯一 revision**，写入无冲突（标准存储 MVCC 语义）；
`row_count not zero` = 同一 key-revision 已存在被重复插入——**并发事务 bug**。

### 异常点 B：watch 推送停摆（静默，无错误日志——推断）

**证据**（间接）：apiserver 65s 无增量（watch cache 无事件可推）+ 所有 watcher（virt-handler/
virt-controller）同时静默 + 恢复后 revision 读取失败——**存储的 watch/增量机制在写风暴下停摆**。

**正常预期**：存储 watch 持续推送增量事件（每次写入 → 通知 apiserver watch cache → 广播客户端）。

### 异常点 C：compact 风暴（结果，非原因）

**日志证据**（本地，18:41:04-06，即停摆后 60s）：
```
I ccdb_driver.cpp:494] compact key: /registry/events/kubevirt/bootdisk-... revision: 99819
I ccdb_driver.cpp:494] compact key: /registry/pods/kubevirt/... revision: 99937
...（大量 compact：events/PVCs/pods/jobs/endpoints）
```
**注意**：发生在 watch 中断（18:40:04.5）**之后 60s**——是停摆后的存储自清理，**不是原因**。

## 7. 结论与修复方向

**根因**：Stop 流程的首批并发写（virt-controller 删 VMI + virt-handler Update）触发后端存储
（ccdb）的并发事务冲突（row_count not zero）→ 存储 watch 推送停摆 → apiserver watch cache
65s 无增量 → virt-handler/virt-controller 收不到 VMI 事件 → virt-handler expectations 卡住
（65s 空白）→ virt-launcher 45s 超时退出 → pod 消失 → 写 Failed → 自动拉起。
**写风暴（5s 循环 + 409 重试）是停摆后的正反馈放大器，非初始原因。**

**修复方向**：
1. **减轻写风暴**（打断正反馈）：virt-handler 409 后不立即重试（等 AddAfter 5s）、vm 控制器 stopRequest 去重
2. **方向B 兜底**：virt-launcher 在 domain 已 shutoff 时不超时退出（即使存储停摆也不重启）
3. **存储治本**：厂商修复并发事务 revision 分配 bug 与 watch 停摆（内部反馈）
