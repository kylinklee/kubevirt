> 中断，当时写入频率正常（写风暴尚未形成）——初始触发机制是什么？"
> 配套文档：`docs/Stop后VMI自动拉起-完整证据链-20260810.md`（组件证据链）、

## 1. 结论摘要

1. **停摆位置已确定**：VMI 事件推送的断点位于 **apiserver 的 watch cache ← 后端存储（ccdb）watch**
   这一段，不在 virt-handler 本地链路（domain 事件同期正常）、不在 apiserver HTTP 层（65s 窗口内
   apiserver 零错误、其他 API 正常）。
2. **初始触发时刻**：10:40:04.5（本地 18:40:04.5）——即 Stop 请求（18:40:04.278）后的**首批并发写**
   （~200ms 内 virt-api PATCH VMI stopRequest / virt-controller DELETE VMI / virt-handler PUT VMI status
   + 3 条事件 POST）落在 ccdb 上、且**最后一条事件（10:40:04.490）送达之后**。
3. **候选机制（二选一，现有证据无法区分传输细节，但都指向 ccdb）**：
   - **H2（存储故障经 apiserver 关流传导）**：ccdb watch/增量服务在首批并发写下失效 → apiserver watch
     cache 源头中断 → 向客户端 VMI watch 流下发 `Aborted` 关闭 → reflector 退出 watch → 立即重发
     Watch（rv=101217）→ 该请求在存储层 **hang 住 43s** → 10:40:47.488 存储部分恢复、请求被服务。
     **43s 重连与"窗口内零 apiserver VMI 活动"的观测吻合**（hang 的请求 httplog 不打点）。
   - **H1（存储 watch 静默停摆）**：ccdb 静默停止向 apiserver watch cache 推送增量，watch 流仍开着、
     无事件 → 与 43s 即重连**不完全吻合**（正常需等 5-10min watch 超时）——除非期间收到了流内错误。
4. **v1.2.0 不触发的差异点（现有证据不能定论）**：两版本 Stop 流程代码逻辑相同；差异候选为
   存储当时状态/负载余量、首批写的时序与并发度、v1.6.6 更多控制器/informer 抬高的基线存储流量。
   这需要验证方案（见 §5）证实/证伪，**不要当作已确认事实**。
5. **写风暴是放大器、compact 风暴是结果**（已确认，不重复）。

## 2. 初始触发机制分析

### 2.1 触发窗口重建（10:40:04.278Z ~ 10:40:04.5Z，UTC）

```
10:40:04.278  virt-api   PUT /stop → 202（Stop 请求落地）
10:40:04.3xx  首批并发写：virt-api PATCH VMI(StopRequest)
                       + virt-controller 删 VMI(DeletionTimestamp)
                       + virt-handler 处理 stopRequest → 后续 PUT VMI status
10:40:04.332  virt-handler 收到 vmi update event（断前倒数第 2 条）
10:40:04.368  virt-controller POST events → 201（apiserver httplog）
10:40:04.377  virt-handler   POST events → 201（apiserver httplog）
10:40:04.439  virt-handler  execute: expectations not satisfied（卡住开始）
10:40:04.466  kubelet      POST events → 201（apiserver 最后一条 VMI 相关 httplog）
10:40:04.490  virt-handler 收到最后一条 vmi update event → 之后 46s+ 零事件
10:40:04.5    ★ 存储 watch/增量服务停摆（首批并发写触发，推断）
```

**说明**：18:40:04.466（本地）之后的 apiserver 日志缺口（"零 VMI 请求"）与 virt-handler 在
10:40:04.490 仍收到事件不矛盾——捕获的 apiserver 日志**可能只来自多副本中的一例**（见 §3 缺口 G1）；
且 VMI 的 PUT/PATCH 本身在窗口内未出现在捕获日志中，指向 VMI 写请求由其他 apiserver 副本服务。

### 2.2 为什么指向"apiserver watch cache ← 存储 watch"这一段

| 观测 | 排除 |
|------|------|
| domain 事件同期正常（10:40:06/12，文件/notify-pipe 本地链路） | virt-handler 本地处理、informer 分派正常 |
| apiserver 65s 窗口零错误、lease/discovery/kubectl 正常 | apiserver HTTP 层健康 |
| virt-controller 也静默 65s（18:40:04.466→18:41:09 零 PATCH/PUT） | 非 virt-handler 独有，全局 watch 停摆 |
| 18:41:28 存储 `Failed to list key's revision`（Aborted）+ `row_count not zero` | 存储侧数据/事务已异常 |

三段排除后，唯一剩余环节就是 **apiserver 的 watch 增量源（存储 watch）**。存储停摆时 apiserver
watch cache 无增量可推，且**流内错误（Aborted）以 watch.Error 发给客户端、httplog 不记录**——
所以 apiserver 日志"干净"是假象。

### 2.3 两个候选机制的证据权重

**H2（存储故障 → apiserver 关流 → 重连 hang 43s）——与"43s 重连"最吻合**

时序推演：
```
10:40:04.5   存储 watch 通知中断（首批并发写触发 ccdb 事务/通知异常）
             apiserver 的 Cacher（watch cache 源头）收不到存储增量
10:40:04.5   apiserver 终止该 key 的客户端 watch 流（下发 Aborted watch.Error）
             —— httplog 不记录流内错误，apiserver 日志"干净"✓
virt-handler reflector 收到 watch.Error → 退出 watch() → 立即重建 Watch(rv=101217)
             —— klog.Warningf("watch ... ended with") 若 klog 未进入捕获日志则不可见（缺口 G2）
10:40:04.5   新 Watch 请求到达 apiserver → 存储层 hang（读 revision 阻塞）
             —— httplog 只在请求完成时打点 → 窗口内"零 VMI 请求"✓
             —— get.go "Starting watch" 在存储 watch 建立后打点 → 未出现✓
10:40:47.488 存储部分恢复，该 Watch 请求被服务 → [debug] starting watch rv=101217 ✓
```
43s 不是"list() 连续失败退避"的必然结论——若曾有多次 list()/watch() 尝试，`[debug] listwatch: listing`
应多次出现；现有探针日志只见一次 starting watch。**"单次请求 hang 43s"与"零 apiserver VMI 活动"
的一致性更高**。（判读依赖缺口 G3：doc_324e 探针日志中是否有多次 listing。）

**H1（存储 watch 静默停摆，流仍开着）——不能单独解释 43s 重连**

若 watch 流仍开、只是无事件，reflector 会一直等到 5-10min 的 watch 超时才重建。观测到 43s 即重建，
因此 H1 若要成立，必须在期间收到某个流内错误或超时——那就回到 H2 的传导路径。**H1 仅作为
"存储侧静默、无显式错误"的存储内部细节保留**，不改变结论。

**共同指向**：两种机制都要求 **ccdb 在首批并发写冲击下 watch/增量与 revision 读写异常**。H1/H2 的
区别只是"存储故障如何传导到客户端"的传输细节，**根因定位不变：后端存储 ccdb**。

### 2.4 为什么 v1.6.6 触发而 v1.2.0 不触发

已确认：两版本 Stop 流程代码逻辑相同（stopVMI、syncRunStrategy RerunOnFailure、updateVMIStatus、
shutdownVMI AddAfter 5s）。**首批写触发**的差异候选（均未证实）：

- **c1 存储余量**：故障发生时刻存储可能已处于临界状态（revision 漂移/碎片），v1.6.6 的某一笔并发写
  成为压垮点；v1.2.0 同期负载未到阈值。
- **c2 首批写时序/并发度**：v1.6.6 组件间首写顺序/重叠度与 v1.2.0 不同（如多副本 apiserver 路由、
  控制器处理时序），导致同一 key 并发事务冲突窗口不同。
- **c3 基线流量**：v1.6.6 运行更多控制器与 informer（migration 独立控制器等），存储基线读写/compact
  压力更高，容错余量更小。

> ⚠️ 以上为**假设清单**，不是结论。区分它们需要 §5 的对照验证，不要写入修复 PR 作为依据。

## 5. 验证方案（证实/证伪）

### 5.1 证实/证伪"首批并发写触发 ccdb 存储异常"（针对 G1）
- **证真**：ccdb 18:40:03-10 窗口出现并发事务冲突/通知异常错误，且与 18:40:04.3-04.5 的首批写
  毫秒级对应 → 结论成立。
- **证伪**：该窗口无任何错误 → "并发事务冲突"不成立，需转向"存储 watch 线程/资源在其他原因下
  失效"（如背压、fd 耗尽、内部队列满）——需 ccdbshim 内部日志配合。

### 5.2 证实/证伪 H1 vs H2（针对 G2/G3/G6）
- **H2 证真**：SIGQUIT dump 显示 reflector 卡在 Watch HTTP 请求；原始日志有 `watch ... ended with`
  warning；apiserver 侧有 Cacher/watch cache 关流或 relist 失败日志。
- **H1 证真**：dump 显示 reflector 仍在 watchHandler 正常等待（流未关）；无 "ended with"；apiserver
  侧无关流日志；43s 重连另有解释（如流被对端超时）。
- **证伪判据**：若重连前的 43s 内存在 ≥2 次 `listwatch: listing`，则原"list() 连续失败退避"解读成立，
  说明 relist 本身反复失败——同样指向存储读失败，只是细节不同。

### 5.3 证实/证伪"v1.6.6 与 v1.2.0 的触发差异"（针对 c1/c2/c3）
- **对照实验**（调试机）：
  - **c1/c3**：在 v1.6.6 下对**非目标 VM**（无历史写负载）执行 Stop，观察是否触发；同时对 v1.2.0
    环境在**人为制造写负载**（批量创建/删除无关 VMI）后 Stop，观察是否触发。可分离"存储余量"与
    "版本特性"。
  - **c2**：在两版本各执行 3 次 Stop，对比首批写（0-500ms 窗口）在 apiserver httplog 中的
    **请求时序/重叠度**（哪类写先落、间隔多少）。
- **判定**：v1.6.6 在低负载下也触发 → c2/c3 可能性上升；v1.6.6 低负载不触发、高负载触发 → c1 上升。

### 5.4 复现实验（最小验证）
- 用测试 VMI bd7b60cbf8e0502c3103d5be570bbe7b 重复 Stop，**开启 §6 探针后**采集：
  ccdb 18:40 窗口、virt-handler 原始 klog、SIGQUIT dump、apiserver 全部副本日志。
- 目标是拿到**第一笔"Update 成功但事件未回"的 rv**，把初始触发的"最后一笔正常广播"与
  "第一笔丢失广播"精确钉在 ccdb 事务上。

### P3 记录 Watch() 建立耗时（区分 43s 空窗成因：hang vs 流静默）

`pkg/controller/controller.go` `NewListWatchFromClient` watchFunc（controller.go:151）：

```go
watchStart := time.Now()
w, err := c.Get().
    Namespace(namespace).
    Resource(resource).
    VersionedParams(&options, metav1.ParameterCodec).
    Watch(context.Background())
if err != nil {
    if debugWatch {
        log.Log.Infof("[debug] listwatch: watch start FAILED for %s: %v", resource, err)
    }
    return nil, err
}
if debugWatch {
    log.Log.Infof("[debug] listwatch: watch established for %s rv=%s in %v", resource, options.ResourceVersion, time.Since(watchStart))
}
```

**判读（区分 H1/H2 的关键）**：
- `starting watch 10:40:04.5` → `watch established 10:40:47.488 in 43s` ⇒ **Watch() 请求 hang**
  （H2 传导：单次请求被存储阻塞 43s，与"窗口内零 apiserver VMI 活动"吻合）。
- `watch established 10:40:04.5`（毫秒级）后直到 10:40:47 无事件 ⇒ **流静默**（H1）。
- 期间出现 `listwatch: listing` ⇒ **list() 连续失败退避**（原文档解读）。

### P4 expectations 拦截处附加 rv（区分"事件已到未清账"vs"事件根本没到"）

`pkg/virt-handler/vm.go` `execute` expectations 拦截（vm.go:327）：

```go
} else if !c.vmiExpectations.SatisfiedExpectations(key) {
    // [claude] 附加 rv：配合 P1/P2 对照"最后到达的事件 rv"，判断跳过时
    // 本地 informer 缓存里 VMI 的 rv 是否已更新（区分事件是否已到）。
    log.Log.Object(vmi).Infof("[debug] execute: expectations not satisfied, skipping reconcile rv=%s", vmi.ResourceVersion)
    return nil
}
```

**判读**：若跳过时 rv 停在 P2 最后到达的 rv ⇒ 事件没到（链路断）；若 rv 已推进到更新值但
expectations 仍未清账 ⇒ 清账环节异常（两者机制不同，P4 直接区分）。

### P1/P2/P4 联合判读（核心）

若 P1 显示 `Update ok rv=101218`、P2 事件流停在 `rv=101217`、P4 跳过时 rv=101217 ⇒
**精确证实 rv=101218 这笔写被存储广播丢弃**——把初始触发钉死在 ccdb 的写入→通知环节。

### 不建议改动的点
- **不要在 watchFunc 中起 goroutine 监听 ResultChan**（会与 reflector 争抢消费同一 channel，破坏
  watch.Interface 契约，历史上已导致 VM 创建失败）。
- **不要改 vendor/client-go reflector**（upstream 代码，改动面大、与诊断无关且禁止无关提交）。
- 若需要 reflector 层信息，用 §4 的 klog grep + SIGQUIT dump 替代。

## 7. 一句话结论

**Stop 首批并发写（18:40:04.3-04.5）冲击后端存储 ccdb，导致其 watch/增量服务失效；apiserver 的
VMI watch 增量源在 10:40:04.5 中断（H2：经 apiserver 关流传导，最吻合 43s 重连观测；H1：存储
静默，未定），其后所有 watcher 收不到事件 → expectations 卡死 → virt-launcher 超时退出 → pod 消失
→ 写 Failed → RerunOnFailure 自动拉起。** 直接证据缺口为 **ccdb 18:40:03-10 窗口日志**与
**virt-handler 原始 klog 输出**；补齐后可在 H1/H2、以及"v1.6.6 vs v1.2.0 差异来源"上定论。
